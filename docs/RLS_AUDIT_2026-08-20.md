### What was broken before the lockdown

Every RLS policy created by `supabase/schema.sql` was `using (true)` with no `TO`
clause — which in Postgres means `TO PUBLIC`, which includes `anon`. The
publishable key is inlined into the browser bundle on every page load, so any
internet user with no auth could:

- `INSERT` / `UPDATE` `signals` → forge rows on the public research feed
- `INSERT` `provider_stats` → forge leaderboard rankings
- `INSERT` `keeper_audit` → forge the "tamper-evident" audit trail
- `INSERT` / `UPDATE` `profiles` → write to a table that stores emails
- `SELECT` `whitelist` → dump every waitlist email ever collected
- `SELECT` `subscriptions` → dump subscriber wallet / tier / spend

An earlier hardening migration (`0035_fix_rls_policies.sql`) did the right
thing, but `schema.sql` was re-run afterwards and its `drop policy if exists`
only ever drops **its own** policy names. Postgres ORs permissive policies
together, so `(true) OR (auth.role() = 'service_role')` collapses back to `true`
and the hardening was arithmetically dead. The 2026-08-07 fix enumerates
`pg_policies` and drops **every** policy per table before rebuilding.

## 2. Founder action item: re-issue the service-role key

Because the publishable (`anon`) key was effectively able to write to every
table, any key value that ever shipped to a browser must be considered
**burned**:

1. In the Supabase Dashboard go to **Project Settings → API**.
2. **Rotate / regenerate** the `service_role` key (the `secret` JWT). The old
   value is invalidated; any deployed environment keeps working only after
   the new value is set there too.
3. The `anon` / publishable key can stay — it now only grants `SELECT` on a
   whitelist of public-display tables, which is what it was always supposed to
   do. (It can still be rotated for hygiene; that's optional.)
4. Update every place the old `SUPABASE_SERVICE_ROLE_KEY` was stored:
   - Vercel project env vars for **production** and any **preview** deployments
   - Local `.env.local` for any operator with repo clone + write access
   - Any CI secret store or password manager
5. Confirm no client bundle still embeds the secret. Grep the production
   deployment for the key prefix — it must not appear outside server
   routes. (`utils/supabase/admin.ts` is the only sanctioned importer.)

> **Never** prefix the service-role key with `NEXT_PUBLIC_`. `NEXT_PUBLIC_*`
> vars are inlined into the browser bundle at build time; a service-role
> key with that prefix silently re-opens every hole the lockdown closed.
> `utils/supabase/admin.ts:30` throws at boot if the env var is missing or
> mis-prefixed — that throw is the gate, do not weaken it.

## 3. Per-table RLS posture (post-lockdown)

Forced on (`alter table … enable row level security`) and all pre-existing
policies dropped on every table listed. Anon / authenticated write grants
(`insert, update, delete, truncate`) are also revoked on every table — defence
in depth so a future policy mistake cannot re-open a write path on its own.

### 3.2 Private tables — anon gets no policy at all

No anon `SELECT`, no anon `INSERT/UPDATE/DELETE`. RLS denies by default.
Service-role writes are the only way in.

| Table | Contents | Anon posture |
|---|---|---|
| `whitelist` | waitlist emails (GDPR personal data) | no anon policy → all reads and writes denied |
| `subscriptions` | subscriber wallet / tier / spend | no anon policy → all reads and writes denied |
| `profiles` | wallet ↔ email mapping | no anon policy → all reads and writes denied |
| `api_keys` | sha256 contributor-key store (authn) | no anon policy → all reads and writes denied |
| `keeper_heartbeats` | keeper liveness / ops | no anon policy → all reads and writes denied |
| `indexer_state` | indexer cursor | no anon policy → all reads and writes denied |

### 3.3 Verify on the live database

After applying `supabase/migrations/2026-08-07_lock_down_rls.sql`, the
following query must return **zero rows**. Anything returned is a regression —
re-run the migration.

```sql
select tablename, policyname, cmd, roles
  from pg_policies
 where schemaname = 'public'
   and cmd <> 'SELECT'
   and ('anon' = any(roles) or 'public' = any(roles));
```

## 4. Server-side write paths (use `SUPABASE_SERVICE_ROLE_KEY`)

Every entry below is the **only** path that can write to the database post
lockdown. The key contract:

- Public reads of public tables → `utils/supabase/server.ts` (anon key, RLS-OK)
- Anything that writes → `utils/supabase/admin.ts` (`createAdminClient`, service-role)
- Reads of private tables (`api_keys`, `whitelist`, `profiles`, `subscriptions`) → service-role

| Route / path | Service-role client | What it writes / reads |
|---|---|---|
| `app/api/cron/heartbeat/route.ts` | inline `@supabase/supabase-js` with `SUPABASE_SERVICE_ROLE_KEY` | reads + writes `keeper_heartbeats` (keeper liveness probe) |
| `app/api/whitelist/route.ts` | `createAdminClient` from `@/utils/supabase/admin` | inserts waitlist signups into `whitelist` (rate-limited per-IP; response carries no row data — see note below) |
| `app/api/research/route.ts` | `createAdminClient` | reads `signals` / writes research pipeline state |
| `app/api/research/execute/route.ts` | `createAdminClient` | writes `execution_attempts`, reads `keeper_audit` |
| `app/api/research/log/route.ts` | `createAdminClient` | appends structured research log rows |
| `app/api/contribute/route.ts` | `createAdminClient` | contributor dashboard server actions |
| `app/api/contribute/api-keys/route.ts` | `createAdminClient` | reads + writes `api_keys` (authn credential store) |
| `app/api/contribute/research/route.ts` | `createAdminClient` | contributor research submission |
| `app/api/contribute/analytics/route.ts` | `createAdminClient` | contributor analytics reads |
| `utils/supabase/middleware.ts` | `createAdminClient` (per request) | session refresh + auth cookie handling |

> **`/api/whitelist` deliberately returns no row data.** Echoing the inserted
> row would turn the endpoint into an email-existence oracle — a third party
> could probe whether an address is on the waitlist by sending a request and
> checking the response. The route returns `{ ok: true }` only.

### What does **not** have a write path here

- The browser bundle. Any client component that imports
  `@/utils/supabase/admin` is a bug; it would either crash at boot (the
  admin-client throws when `SUPABASE_SERVICE_ROLE_KEY` is missing) or, if a
  misconfigured build ever inlined the key, re-open every hole the lockdown
  closed. The founder can grep the deployed bundle to confirm
  `SUPABASE_SERVICE_ROLE_KEY` never appears outside server routes.
- Direct INSERT / UPDATE / DELETE from any Supabase SQL editor not run via
  the lockdown migration. The lockdown is idempotent and re-runnable; if a
  new migration needs to add a write policy, it must use the same pattern
  (`drop every policy then re-create`), not `drop policy if exists <name>`.
